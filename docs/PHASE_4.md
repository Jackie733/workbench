# 阶段 4：实施计划、代码结果与验证证据

日期：2026-11-12。插件 3.3.0。已实现计划、实施基线、Git 观察结果、真实差异、验证命令证据与失效状态；阶段 5 的审查／人工验收／审计和阶段 6 的迁移仍未实现。

## 范围

- 需求级计划：稳定步骤 ID、动态增改与状态、阻塞原因；不制造虚假固定百分比。
- 实施基线：来源端在发送前记录 HEAD、工作区指纹和实际改动／未跟踪文件；只有发送回执 `submitted` 后才保存。
- 结果页：读取 HEAD 以来的提交、文件变化与 48 KiB 内真实差异，明确标注归属无法由 Git 证明。
- 验证证据：在项目根目录执行用户明确填写的命令，保存退出码、输出、关联验收条件与代码快照指纹。
- 代码或验收条件变化后，旧验证标记为已失效但保留历史。

## 数据

```text
<repo>/.omp/workbench/requirements/<id>/
  plan.json
  results.json
  evidence/verification-<id>.json
```

`plan.json`（schema 1）包含 `revision, designVersion, steps[], changeReason, updatedAt`。步骤：

```text
id=step-<hex>, title, status=pending|active|done|blocked|skipped,
reason, updatedAt, evidenceIds[]
```

最多 40 步；`revision` 使用门控 CAS，并发冲突拒绝覆盖。步骤 ID 一经创建不再改变；新增步骤只增加总数，界面显示“已完成 X / 共 Y”，不计算百分比。设为阻塞必须填写原因；改为其他状态清除原因。

`results.json`（schema 1）包含：

- `baseline`：请求 ID、HEAD、指纹、捕获时间、工作区是否已有改动、基线文件清单（最多 256 个，含工作区 SHA-256）。
- `changes`：当前 HEAD、指纹、提交（最多 50）、文件清单、差异文本／SHA-256、差异或清单是否截断。
- `verifications[]`：证据摘要，完整输出在 `evidence/`。

`baseline` 与 `changes` 的文件路径限制在项目相对路径，拒绝控制字符；差异上限 48 KiB，超过时明确标记截断，不冒充完整差异。验证摘要最多 50 条；输出预览每条 400 字节，完整证据 stdout/stderr 各 16 KiB，超限明确标记。

验证记录字段：`id, command, cwd, criterionIds[], requirementRevision, codeSnapshotSha256, startedAt, endedAt, exitCode, timedOut, result, stdoutPreview, stderrPreview, stdoutBytes, stderrBytes, stdoutTruncated, stderrTruncated, evidencePath`。结果只写入 `passed / failed / unknown`；`stale` 由界面按当前快照计算，不改写历史。

## 来源端 Git 观察

新增只读检查操作 `changes`（可带 `since` HEAD）。它返回：

- `gitBaseline` 的真实 HEAD、指纹和文件清单；文件哈希只读取工作区常规文件，不跟随符号链接，单文件 512 KiB、总计 4 MiB 上限；业务目录 `.omp/workbench` 始终排除。
- `git diff HEAD`（未提交＋已暂存）与最多 24 个未跟踪文件的新文件差异；总差异 48 KiB 上限。
- `since..HEAD` 的提交（哈希、时间、作者、主题），最多 50 条。

命令形状严格校验：`operation=changes` 只允许 `since`（空或 7–64 位小写十六进制），其他字段拒绝。检查只读，不执行验证、不写文件。

## 验证执行

结果页要求用户填写命令并显式点击“先取代码快照，再运行验证”：

1. 来源端重新读取当前 `changes`，保存代码快照指纹；此步骤失败则不执行命令。
2. 工作台通过 `wsl.exe -d <distro> --cd <项目根> -- bash -lc <命令>` 启动进程，超时 180 秒。命令由用户原样输入，工作台不从需求正文、方案或路径拼接 shell；用户必须自行审查命令。
3. 完成后记录真实退出码（超时为 null）、stdout/stderr 与预览，写入不可变证据文件，再把摘要追加到 `results.json`。
4. `exitCode=0` 显示“命令成功”，非 0 显示“命令失败”，超时或无退出码显示“结果未知”；这只代表该命令，不构成人工验收。
5. 自动再次读取代码变化，更新当前指纹。

失效规则：

- 当前需求 `revision` 与验证记录不同 → 已失效（验收条件可能变化）。
- 当前 `changes.fingerprint` 与验证的 `codeSnapshotSha256` 不同 → 已失效（代码在验证前后变化）。
- 历史记录、输出和证据文件保留；重新验证会追加新记录。

## 归属与基线

- 发送实施请求时，只有来源回执 `submitted` 才保存基线；失败或未知不写基线。
- 基线已有脏文件只显示为“实施前状态”，不标为本需求产出。
- 结果文件按基线文件清单分类为“基线时已存在，内容未变”“与基线改动混合”“基线后新增”；三类都只是 Git 观察，不证明作者。
- 实施后的外部编辑、用户手动修改和模型修改无法精确区分；界面明确说明归属未知。
- 提交只读取和展示，不自动提交、合并、推送或修改 Git 配置。

## 当前限制

- 验证由工作台启动，不是从 omp 工具事件自动提取；命令、环境与用户终端相同，输出可能含敏感信息，仅做长度限制，不保证脱敏。
- 没有自动测试发现、CI 集成或失败重试；命令超时或崩溃为未知，不推断通过。
- 不自动提交、合并或推送；提交列表只作观察。
- 归属只能到文件／快照级别，不能到行级作者；同文件混合编辑明确标为混合。
- 计划步骤只能新增或改状态，不支持删除或重排；证据与步骤的自动关联留给后续阶段。
- 结果记录上限：文件 256、提交 50、验证 50、差异 48 KiB；超限明确截断，不表示完整证据。
