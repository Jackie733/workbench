# R4b 设计：内容身份与显式生命周期转换（未实施）

- 日期：2026-11-13
- 状态：设计，等待真实桌面验收后实施。没有新增字段、没有迁移、没有改变阶段语义。
- 依据：[重设计提案](REDESIGN_PROPOSAL.md) §4.2-§4.3、[实施计划](REDESIGN_IMPLEMENTATION_PLAN.md) R4b（E8）。

## 1. 问题

实体 `revision` 是 CAS 版本：任何写入（包括阶段变化、回执、元数据）都会递增。批准、验证证据与验收目前都绑定 `revision`：

- 批准记录保存 `requirementRevision` 与 `requirementContent` 摘要；阶段变化后 `revision` 增加，批准即使内容未变也会显示失效。
- 验证证据保存 `requirementRevision`；任何后续阶段写入都会使“当前快照上的通过证据”失效。
- 验收检查同时依赖需求修订与全局代码指纹。

结果是：与批准／证据输入无关的写入也会使授权和证据失效，用户被迫重复批准或重跑验证；同时，任何“为了不失效而不写 revision”的捷径都会削弱审计。

## 2. 目标与边界

- 引入**内容身份**（content identity）：只在定义明确的批准／证据输入变化时改变；与 CAS `revision` 分离。
- 生命周期转换（阻塞／解除／取消／重开）可以写实体 revision，但**不**改变内容身份，因此不撤销与内容无关的授权或证据。
- 不追溯伪造历史：旧记录在升级后仍按旧规则判断，直到新写入建立内容身份，或明确标注不可比较。
- 不引入自动推进：转换只能由用户显式触发；被动观测、idle、readiness 不写生命周期。

## 3. 内容身份的初始字段集

保守集合与现有 `requirementContent` 一致：标题、类型、优先级、目标、范围、验收条件（ID、描述、必需／信息性）、标签。

- 身份 = 该序列化的 SHA-256（已有 `requirementSha256`）。
- 不纳入：阶段、阻塞原因、时间戳、标签以外的展示元数据、Git 基线、代码快照。
- 方案版本、代码快照、执行授权仍是**独立输入**，不合并进一个总分。

## 4. 消费者矩阵

| 消费者 | 当前依据 | 目标依据 | 兼容行为 |
| --- | --- | --- | --- |
| `Validity.approval` / `Workflow.approvalState` | 修订 + 内容串 + 最新方案 | 内容身份 + 方案版本／指纹 + 撤销状态 | 旧批准无内容身份时按现有“修订 + 内容串”判断；不升级为有效 |
| `Validity.verification` | `requirementRevision` + 代码快照 | 需求内容身份 + 代码快照 | 旧证据无身份时仍按修订比较；保留为历史 |
| `Validity.acceptance` / `Review.acceptanceGate` | 修订 + 快照 + 必需条件 + 阻断发现 | 内容身份 + 快照 + 条件 + 发现 | 同上；无法比较时拒绝，不猜测 |
| `Acceptance` 记录 | `requirementRevision` + 快照 | 内容身份 + 快照 | 新记录写身份；旧记录按旧规则展示 |
| 请求意图（`workflow.requests`） | 修订 + 内容串 | 内容身份 + 载荷指纹 | 已存在内容串；新增身份需版本化 |
| `omp/handoff.ts#approved` 与 `resolve` | 修订 + 内容串 + 基线 | 内容身份 + 基线 + 方案 | 脚本侧与 Luau 同步；否则两端判断会分叉 |
| 审计／导出 | 修订 | 显示修订与内容身份（截短） | 旧事件不补造身份 |
| 恢复／迁移脚本 | 字段白名单 | 新字段白名单 + 版本 | 未知版本只读，不回退、不重置 |

## 5. 生命周期转换

| 触发 | 写入 | 内容身份 | 授权／证据 | 禁止 |
| --- | --- | --- | --- | --- |
| 标记阻塞 | 阶段 = blocked，保存原阶段与原因 | 不变 | 不变；界面不得暗示执行已停止 | 在有待核对请求时静默阻塞 |
| 解除阻塞 | 阶段 = 原阶段，保留历史（审计追加或字段保留） | 不变 | 按当前输入重新评估；已失效的批准不得复活 | 自动切到实施中 |
| 取消 | 阶段 = cancelled，保存原因 | 不变 | 保留；不得宣称进程终止 | 取消即删除证据或隐式重开 |
| 重新打开 | 保留验收历史，进入可操作阶段 | 只有内容被编辑才改变 | 不继承旧验收为当前 | 自动重新批准 |
| 接受／驳回 | 记录人工决定 | 不变 | 接受后仍以当前事实复核 | 用审查通过代替验收 |

实现顺序：先内容身份（读旧写新），再转换；两者都要求源端与宿主同步，否则出现“界面有效、源端拒绝”或反之。

## 6. 存储与恢复

- 实体 schema 增加版本；新字段（内容身份／取消原因）只在批准变更的实体上写入新版本。读取器先支持两种版本，旧二进制遇到新版本必须报错只读，不能假设可降级。
- 写入仍用现有 CAS 与锁；跨文件更新（阶段 + 记录）保持单文件优先，必要时用现有恢复协议；不新增第二套日志。
- 升级中断：未完成的新版本文件不可被当作有效记录；旧版本继续可读；不重复执行外部任务。
- 回滚边界：文档必须写明“新写入后旧二进制只能只读”，不承诺降级写入。

## 7. 验收场景（实施时）

- V02：查看／重算 readiness 不写修订。
- V13：v1 与混合版本项目；未知字段／版本；升级中断；旧二进制在新写入后只读。
- V14：阻塞／解除／取消／重开分别在有活动请求、已授权、已验收后执行；原因与历史保留；不宣称终止进程；失效授权不复活。
- V01：内容身份改变后批准、证据与验收一致失效；阶段写入不使它们失效。

## 8. 未决问题

- 取消原因与阻塞历史是追加事件还是单字段：追加需要事件日志或新文件，单字段会覆盖历史。
- 旧证据是否允许用户显式“重新绑定内容身份”：目前倾向不允许，只能重新验证。
- 内容身份的展示粒度（完整哈希、短哈希、仅“已变化”）。
- 源端与宿主版本偏差时的降级策略：拒绝新意图还是只读预览。

在这些问题确定前，不实施 R4b；当前生产基线仍是全局失效（修订 + 快照），已由 R0 的共享评估统一。
