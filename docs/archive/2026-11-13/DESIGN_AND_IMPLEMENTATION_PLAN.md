## 1. 产品定位与不可变约束

### 1.1 定位

按独立产品的质量设计，作为 Tern 内的项目级需求交付工作台运行，而不是另建 Web 应用或重型项目管理系统。

管理每个需求从提出、澄清、设计、实施、验证、审查到验收的全过程，保存其资料、决定、结果和证据；实时呈现当前 omp 的工作状态。

工作台不是另一个 agent，也不是聊天记录镜像。

### 1.2 已确认的约束

1. 默认只有两个窗格：左侧现有 omp，右侧工作台。
2. `/wb` 原位打开或恢复工作台，不新增 omp 进程、标签页或系统窗口。
3. 需求讨论、设计、实施、验证和审查复用同一 omp 会话及其上下文。
4. 新建需求只创建资料，不开始推理，不新建执行会话。
5. 工作台实时知道 omp 的状态、当前动作和可观测的计划进度，而不是只显示静态表单。
6. 不改全局模型配置，不恢复 `@design/@execute`，不自行调用模型 API，不引入 Provider、额度或凭据管理。
7. 任务切换不自动切换 omp 会话；向同一上下文提交另一个需求前明确显示目标和影响。
8. 草稿自动保存不等于发送；关键操作必须由用户明确触发。
9. 模型回合结束、工具成功、验证通过、人工验收是不同事实，不相互替代。
10. 单用户、单项目工作流内只允许一个被工作台认领的活动请求；不宣称能控制外部编辑器或其他 agent。

### 1.3 职责边界

| 部分 | 负责 | 不负责 |
| --- | --- | --- |
| omp | 讨论、设计、代码修改、运行验证、审查 | 作为唯一的任务资料数据库 |
| 工作台 | 需求生命周期、版本、交接、实时观测、结果与审计 | 替代对话、推理和模型路由 |
| Git | 代码、提交、分支与工作区事实 | 证明某次改动一定由某个需求产生 |
| 用户 | 取舍、批准、接管、审查和最终验收 | 手工搬运每次聊天交付 |

首个完整交付范围不包含多人协作、云同步、多代理调度、自动合并、推送、发布及复杂报表。阶段 1 只是技术验证，不作为完成品发布；后续阶段仍属于已确认范围。

## 3. 界面与信息架构

### 3.1 双窗格布局

左侧保留当前 omp，右侧为持久工作台。允许拖动并记忆比例。右侧空间不足时切换页面、折叠次要信息或打开原生文件查看，不创建第三个常驻窗格。

关闭工作台只收起面板，不中断或关闭 omp。再次 `/wb` 恢复原面板，不重排无关窗格。原位目标必须明确，不能退回“第一个窗口”或当前碰巧获得焦点的窗格。

工作台内使用原生可编辑组件，不将 Canvas 当作完整文档编辑器。host/window 的具体职责在阶段 1 原型中确定；必须保持用户眼中始终是一个稳定面板，而不是多个来回替换的临时界面。

### 3.2 顶层导航

2026-11-13 用户明确同意用本节替换原“看板／需求／运行／审计”四个顶层目的地（charter §10 的范围变更程序）。

- **需求**：唯一的需求数据集，筛选、排序、选中项共用；List／Board 是同一数据集的两种布局，不是两个目的地。
- **活动**：跨需求事件检索与导出。
- **会话**：被绑定 omp 的观测任务、工具、绑定细节与诊断；需求归属未知时明确标注未知，不猜测关联。

“需要处理”是由领域记录派生的投影（未解决的可执行条件），不是第四个目的地，也不是未读通知中心。

项目名、绑定会话、连接健康和当前请求归属应始终可见。实际模型未知时显示未知，不猜测、不擅自切换。文案暂用中文；i18n 不在本轮范围。

### 3.3 看板

看板是“需求”目的地的 Board 布局：默认列按持久阶段分组，卡片显示编号、标题、优先级、阶段、当前运行状态、需要处理的事项和最近更新时间；readiness 只作为与列清晰区分的徽章。无法到达的空列不假装存在工作流，未知或旧阶段值保留在显式回退组。

已阻塞和已取消通过独立筛选展示，避免默认列过多。方案版本、变更及验证摘要只在有真实数据时显示。

拖动只改变排序或执行允许的低风险状态调整。批准方案、开始实施、验收等有门禁的转换不能靠拖拽绕过。

### 3.4 需求工作区

| 页面 | 内容 |
| --- | --- |
| 需求 | 背景、场景、目标、范围、验收条件、约束、附件和选定讨论摘录 |
| 方案 | 正式方案版本、差异、风险、批注、批准与失效原因；“准备交接”是次动作内联面板 |
| 交付 | 实施步骤、基线、真实 diff、验证证据与命令准备 |
| 验收 | 审查发现、处置结论、门禁证据与人工接受／驳回／重新打开 |
| 历史 | 该需求的事件时间线与导出，与“活动”是同一事件流 |

工作区顶部只保留只读 readiness 摘要（含缺失动作）与一个主操作；概览并入顶部摘要，不再单独成页。返回来源、滚动、筛选与布局的恢复规则见 [重设计提案](docs/REDESIGN_PROPOSAL.md) §3.1。

每个页面只突出一个主操作。复杂操作放入上下文菜单，不新增一组全局 slash 命令。

### 3.5 交互规则

- 中文多行输入、IME、选择、粘贴、撤销和键盘导航必须可用。
- 草稿自动保存，未发送与已提交清楚区分。
- 正文只展示一处；长文有界滚动，预览截断必须提示并能查看全文。
- 不把截短预览当作完整发送资料。
- 发给 omp 前显示目标会话、项目、任务、资料版本和实际内容。
- 默认放入输入框，用户仍可补充后发送；也允许明确点击发送。
- 不覆盖 omp 已有草稿；冲突时保留两份，由用户处理。
- 忙碌时保持待提交，不默认 steer 打断，也不偷偷排队。
- 中断只在明确操作后执行，不回滚文件，不声称保证终止所有后台工作。

## 4. 需求生命周期与门禁

### 4.1 阶段

| 阶段 | 进入条件 | 正常出口 |
| --- | --- | --- |
| 需求池 | 需求已保存，尚未开始 | 澄清中，或明确选择快捷实施 |
| 澄清中 | 已提交讨论或用户正在补充 | 设计中 |
| 设计中 | 正在形成方案 | 待批准 |
| 待批准 | 存在明确可审阅的方案版本 | 批准后实施中；退回设计中 |
| 实施中 | 批准有效，或已明确授权直接实施 | 验证中 |
| 验证中 | 有待执行的验收检查 | 失败回实施中；证据就绪后待验收 |
| 待验收 | 交付和必要证据齐备 | 人工完成验收；或驳回实施中 |
| 已完成 | 用户明确验收 | 明确重新打开后继续处理 |
| 已阻塞 | 记录阻塞原因和原阶段 | 解除后返回原阶段；必要时重新澄清 |
| 已取消 | 用户明确取消并记录原因 | 明确重新打开 |

审查作为验证／验收中的独立活动记录，不强迫每个小改动都调用模型审查。若某需求把审查设为必需，则未解决的阻断项必须处理或由用户明确豁免并留痕。

### 4.2 核心规则

- 阶段、运行状态、连接状态分开建模。实施中的需求可以是运行、等待用户、停止或断开，不能混成一个字段。
- 批准引用具体需求版本、方案版本和内容指纹。需求范围、验收条件或方案变化使相关批准失效。
- 开始实施前核对批准和工作区基线；变化不能静默接受，须展示差异并重新确认。
- 正式实施之后产生的预期代码变化不会反过来自动撤销本次执行授权。
- 快捷实施可跳过正式方案，但必须保存验收条件、范围和明确授权，不能形成未批准实施的漏洞。
- omp 回合结束不等于需求交付，更不等于验证通过。
- 验证失败时记录具体证据并使当前验证结论失效，不根据普通工具错误随意改变整个需求阶段。
- 已完成只能由人工验收触发；审查通过不能代替验收。
- 同一上下文不等于独占归属。用户手动介入时记录共享上下文，不能把随后全部活动自动算进当前需求。

## 5. 数据模型与存储

### 5.1 项目资料布局

目标布局：

```text
<repo>/.omp/workbench/
  project.json
  requirements/
    REQ-0008/
      requirement.json
      requirement.md
      designs/
        v1.md
        v2.md
      plans/
        current.json
      runs/
        <request-id>.json
      evidence/
        verification-001.json
      reviews/
        review-001.md
      events.jsonl
```

编号在项目内唯一。目录和所有持久实体带 `schemaVersion`；迁移不能静默丢弃未知或损坏数据。

本机临时目录保存请求传输、回执、连接和高频运行状态；不把计时器、每次重绘或逐 token 更新写进项目审计。

### 5.2 核心实体

| 实体 | 关键字段 |
| --- | --- |
| Project | 稳定 ID、Git 根目录、名称、仓库标识 |
| Requirement | 稳定 ID、展示编号、标题、类型、优先级、阶段、修订号、目标、范围、验收条件、标签、时间 |
| DesignVersion | 版本、来源请求、正文指纹、草稿／提议／获批／被替代状态 |
| Approval | 需求修订、方案版本及指纹、基线引用、操作者、时间、失效原因 |
| Plan | 关联需求和方案、稳定步骤 ID、步骤状态、变更说明和证据引用 |
| Run | 请求 ID、需求 ID、会话 ID、活动类型、实际模型、状态、起止时间 |
| Change | 起始 HEAD、工作区快照、关联提交、文件清单、diff 引用和指纹 |
| Verification | 命令及参数、cwd、退出码、时间、必要输出、结论及适用版本 |
| Review | 来源、发现、严重度、处理结论及豁免依据 |
| Acceptance | 接受／驳回、对应版本、说明、操作者和时间 |
| AuditEvent | 事件 ID、序号、时间、操作者、类型及实体引用 |

`requestId` 和工作台任务关联标识由工作台生成，不冒充 omp SDK 自带的请求 handle。保留 omp 自身的 turnIndex、toolCallId 等作为观测字段，不将其当作跨请求全局身份。

### 5.3 Git、隐私和归属

工作台资料可以由用户选择纳入 Git，但不能声称“默认不提交”就代表不会被 `git add .` 收录。初次初始化提供项目本地隐私设置，明确预览后可将该目录加入当前仓库的 `.git/info/exclude`；不改全局 Git 配置，不覆盖用户规则。

开始实施时记录 HEAD 和已存在的未提交／未跟踪改动。后续展示基线以来的变化，但对混合在同一文件、同一行的用户编辑不能宣称精确作者归属。外部改动或归属不确定时明确标识，允许人工关联。不能把整个工作区变化都标成该需求产出。

代码验证结论关联具体快照；相关代码或验收条件变化后，旧结果保留为历史，不能继续显示为当前已验证。

### 5.4 写入与恢复

- 单个项目只允许一个活动写入协调者；其他窗口只读或明确接管。并发冲突不得采用静默最后写入覆盖。
- 实体使用原子替换；事件日志追加。跨文件更新采用可恢复提交记录或等效简单事务协议，具体实现需在阶段 0 定案。
- 发布前必须验证中断发生在事件／实体写入之间时可恢复，不重复执行外部任务。
- 审计通过应用界面只追加，更正另起事件；这不是防篡改安全日志。用户仍能编辑本地文件，内容指纹也不提供操作者真实性证明。
- 版本文件不能原地覆盖历史。草稿与正式版本分开；删除敏感数据时明确影响并保留必要的删除记录，不保存已删除正文副本。

## 6. 实时驱动与集成契约

### 6.1 组成

1. **omp extension**：注册 `/wb`、获取当前会话身份、接收交接、预填／发送、上报生命周期和工具活动。
2. **Tern 插件**：双窗格布局、看板、需求详情、运行、审计，以及原生文件／Git 查看。
3. **本地事件桥**：传递命令、回执和有序事件，不成为新的业务数据库。
4. **项目存储**：保存需求、版本、证据、审查和验收。

优先使用最小本地桥接，不新增常驻 HTTP 服务；文件消息盒、原生控制接口或其他通道的最终选型必须以 Windows／WSL 原型证据为准。实现文档必须记录所选通道、替代方案被排除的原因和失效处理，不把候选方案误称为现成能力。

### 6.2 来源身份

绑定地址至少区分本次桥接实例、Tern 窗口／pane 和 omp session。cwd 是属性，不是身份。

从每次 omp handler 的实际 context 读取会话 ID；不能把模块级 `currentSession/currentTask` 当作所有子会话共享的来源。一个 pane 内 `/new`、resume 或 fork 后不能继续向旧绑定静默投递。

来源缺失或匹配不唯一时拒绝自动布局／发送，并允许用户明确选择一次绑定；绝不回退到第一个窗口、同目录任意空闲 omp 或 `@focused`。

### 6.3 事件与状态

下面是目标协议，不表示 SDK 已原生提供同名事件：

```text
session.bound / changed / disconnected
request.created / accepted / started / waiting_user / ended / failed
request.delivery_unknown
request.cancel_requested / cancelled

tool.started / finished
plan.updated
artifact.proposed
design.version_created
verification.started / finished
review.created
acceptance.recorded
```

传输信封包含事件 ID、来源序号、时间、项目、会话、需求和请求引用。没有任务归属的会话事件允许无需求／请求引用，不能为了填满字段而猜测。

区分本地待提交、目标接收、实际开始消费、运行结束、交付、验证和验收。`sendUserMessage` Promise 的返回不能直接作为统一完成契约。

异步回调进入每个来源的有序发送队列，不能依赖不同事件 handler 完成的先后顺序。事件 ID 去重；序号缺口触发快照核对，不自动重发执行命令。

### 6.4 计划、交付与验证

- 当前动作来自真实工具事件和 Tern／omp 生命周期。
- 步骤来自可关联的计划更新；若 SDK 没有可靠现成来源，使用显式的工作台结构化更新契约。不得通过关键词猜测自然语言中的完成状态。
- 步骤增删保留稳定 ID 和修改说明，不把计划总数视为永远不变。
- 分母可靠时显示已完成／总数；否则只显示当前步骤，不制造进度百分比。
- 普通 assistant 回复先作为候选交付；只有明确归属且被采用的正文才形成方案版本。
- 工具 `isError=false` 不代表测试成功。验证需解析实际命令结果、退出码和适用快照；无可靠退出码时只能是待核实证据。
- 运行结束事件若仍有继续执行或后台工作，不标记终态。单纯 idle 不代表交付完成。

### 6.5 恢复与延迟

- 初始性能目标：连接健康时，状态变化在 1 秒内出现在面板；真实跨 Windows／WSL 测量后记录延迟与调整依据。
- 高频事件合并显示，不反复跨 WSL 启动进程读取相同状态。
- 断开后显示过期时间和最后已知状态，不能继续假装实时。
- 重载后核对实际 session、运行请求、资料和 Git 快照；不自动恢复旧审批或重新发送任务。
- 发送是否成功不确定时进入 `delivery_unknown`，由核对／人工决定恢复，不以“重试”掩盖重复执行风险。
- 无法观测的活动显示未知，不能用 Tern 运行状态推导精确任务归属。

## 7. 端到端用户流程

### 7.1 记录与澄清

1. 在现有 omp 输入 `/wb`。
2. 新建需求，填写目标、场景、范围和验收条件。
3. 选择文件、文档片段或讨论摘录；不自动发送完整聊天。
4. 保存到需求池。明确提交后才进入澄清活动。
5. 工作台展示实际目标和发送内容；有输入草稿时不覆盖。

### 7.2 方案与批准

1. 向同一会话提交设计请求。
2. 形成明确归属的候选交付或项目内方案文件。
3. 工作台读取并展示方案，采用后形成不可覆盖的版本。
4. 用户批注、退回或批准具体版本。
5. 相关需求／方案变化使批准失效；批准本身不必立即启动实施。

### 7.3 实施与验证

1. 明确点击开始实施，核对批准、范围、基线和目标会话。
2. 记录请求身份，提交给同一个 omp。
3. 实时显示工具、步骤、等待输入和阻塞原因。
4. 结果页从真实 Git 读取变化，区分原有改动和归属不确定的变化。
5. 保存实际验证命令、结果和适用代码快照；失败返回处理，不自动重试模型请求。

### 7.4 审查与验收

1. 可打开 omp 原生 `/review` 并明确选择范围；不复制另一套审查引擎。
2. 审查发现进入工作台，关联处理结果或明确豁免。
3. 用户检查验收条件、交付和证据后接受或驳回。
4. 接受才进入已完成。可按需求导出 Markdown 摘要和引用的证据，默认不打包凭据或完整聊天。

## 8. 安全与权限边界

- 不读取或保存模型密钥、登录信息，不改变 Provider、fallback 或默认模型。
- 项目数据写入限制在当前已确认根目录；本地运行文件与传输凭证位于当前用户私有目录。
- 校验规范路径、符号链接、项目身份和发行版，防止路径穿越。Windows／WSL 路径不得靠替换字符串任意信任。
- 用户选择项目外附件时，需显式确认其内容范围；不能让外部附件改变工作台写入根目录。
- 本地 IPC 只信任已绑定实例并校验消息结构、长度和身份；具体访问控制随桥接方案一并验收。
- 命令使用结构化参数，不将需求正文、路径或方案拼接进 shell。
- 内容和日志限制体积；截断明确标识。敏感输出支持不保存或删减，不能宣称自动脱敏绝对可靠。
- 设计阶段只研究的提示词不是 OS 沙箱，工作台审批门禁也不能阻止用户直接在 omp 中执行代码。需要强工具权限时复用经过验证的 omp 原生机制，不伪造保护。
- 不自动提交、合并、推送、发布，不自动修改 `safe.directory`。

## 9. 分阶段执行计划

各阶段按依赖顺序实施。每阶段都要有真实证据和明确退出条件；不以编译通过替代交互验收。

### 阶段 0：领域规范与迁移设计

交付：

- 固定实体 schema、状态转换和门禁。
- 固定请求／事件信封、来源序号与去重规则。
- 决定单项目写入协调、原子写入和崩溃恢复协议。
- 记录现有 KV 与 `.omp/workbench/tasks` 数据格式和迁移映射。
- 固定隐私策略、导出范围和旧审批失效规则。

验收：

- 用一个完整样例表示需求、方案、批准、执行、验证、审查和验收。
- 快捷实施、阻塞恢复、驳回、重新打开及未知发送状态均有明确转换。
- 所有已确认范围都映射到后续阶段，不静默删减。

### 阶段 1：会话绑定与实时闭环原型

交付：

- 轻量 omp extension 注册 `/wb`。
- 原位打开右侧工作台，关联实际调用会话。
- 证明所选本地通信方案在 Windows Tern＋WSL 中可用。
- 真实展示运行、等待输入、空闲、断开和工具起止。
- 证明工作台能向同一会话预填／明确提交，并收到有序关联回执。
- 证明计划／交付归属的实现路径，而非只展示普通运行状态。

验收场景：

- 重复 `/wb` 不增加 omp、标签页或工作台副本。
- 两个 Tern 窗口中操作不会落到错误窗口；身份不足时明确拒绝。
- 中文及空格路径正常；不套额外 `wsl.exe` 破坏原生 TSP。
- 手动运行一条实际命令，面板出现正确工具状态和结果；测量同步延迟。
- `/new`、resume、fork 后旧绑定失效或经明确确认更新。
- 目标忙、已有草稿、断开、重载、重复事件和不确定发送均不导致覆盖或重复执行。
- 不修改模型配置、凭据或用户现有会话内容来通过探针。

阶段门禁：上述来源与实时闭环若无法证明，先解决或列出确切外部阻塞，不继续堆看板界面。原型不是最终产品。

### 阶段 2：项目存储、需求池与看板

交付：

- 项目初始化与隐私设置、需求编号和修订。
- 新建、编辑、搜索、筛选、排序与看板。
- 原生中文草稿自动保存与恢复。
- 需求详情基础框架、单项目写入协调和损坏数据保护。

验收：

- 重载后需求、草稿、选中项保持完整。
- 看板和详情共用事实来源，不出现相互矛盾状态。
- 非法拖拽不能绕过批准／验收。
- 多窗口写入冲突被阻止或明确接管，无静默丢数据。
- 写入中断恢复不会损坏其他需求或触发模型调用。

### 阶段 3：资料提交、方案版本与批准

交付：

- 需求、文件和讨论摘录的选择与完整发送预览。
- 输入框预填／明确发送、已有草稿冲突处理。
- 候选方案、正式版本、差异、批注、批准与失效。
- 快捷实施授权。

验收：

- 不把无关聊天或下一条回复自动认作方案。
- 全文未被预览截断影响；路径、大小和身份错误明确拒绝。
- 需求、验收条件或方案变化使旧批准失效。
- 未批准方案不能通过工作台启动实施；快捷实施有独立明确授权。
- 重载、重复点击和未知回执不重复发送。

### 阶段 4：实施计划、代码结果与验证证据

交付：

- 稳定步骤 ID、动态计划、实时动作与阻塞。
- HEAD 和工作区基线、提交关联、文件变化及原生 diff。
- 验证命令、退出码、输出、适用快照和失效状态。

验收：

- 在临时 Git 项目中真实完成一次代码修改和针对性验证。
- 原有未提交改动、实施后外部编辑和归属不明变化均不被冒称任务产出。
- 计划中途调整不会制造错误百分比。
- 工具成功但测试失败时不能显示验证通过。
- 验证后的代码变化使旧结果不再作为当前已验证证据。
- 回合结束但仍有后台工作时，不自动交付或验收。

### 阶段 5：审查、人工验收、审计与导出

交付：

- 原生 `/review` 范围入口与明确提交，不重复实现审查引擎。
- 审查发现、解决记录、豁免和阻断规则。
- 人工接受／驳回、重新打开。
- 按需求审计时间线、检索及 Markdown 导出。

验收：

- 一条需求可追溯到采用的方案、批准、执行、代码、验证、审查和验收。
- 普通编辑不能覆盖应用内历史；更正追加记录。
- 不宣称本地日志不可篡改。
- 模型自行说完成、审查通过、会话 idle 都不能替代人工验收。
- 导出不夹带认证数据、未选择的聊天或敏感输出。

### 阶段 6：迁移、清理与真实发布验收

交付：

- 显式迁移旧 KV 任务和项目方案，保留源数据备份及映射。
- 老状态按证据保守映射；所有旧审批失效，运行态标记待核对。
- 删除已被替代的角色启动、额外 omp split 和旧入口逻辑；保留用户既有会话，不主动关闭。
- 更新 README、使用说明、协议说明与变更记录，清除原型和临时探针。
- 在用户明确选择的真实项目中完成全流程验收。

验收：

- 旧任务和产物无静默丢失，重复迁移不产生副本。
- 默认全过程只有原 omp＋工作台，无隐藏角色路由。
- 单个真实需求完成记录、设计、批准、修改、验证、审查／明确跳过和人工验收。
- 关闭、重载、断开、重新绑定恢复真实状态，不重发请求。
- 未通过的命名验收项不能以“后续完善”改称已交付。

## 10. 验证策略与执行纪律

- 文档阶段只校验文档保存、链接与范围；不启动或修改运行中的用户会话。
- 实现先读现有代码及当时已安装版本的 SDK 契约，不凭本文构造不存在的 API。
- API 能力探针使用隔离临时 Git 项目和用户允许的会话，不向日常会话灌入测试需求。
- UI 必须在真实 Windows Tern 上操作并保留截图／状态证据，覆盖中文输入、窄面板、滚动与恢复。
- 业务规则只为实际风险增加确定性回归测试：门禁、归属、乱序、重复、路径、恢复、迁移和证据失效。
- 不增加测试源码文案、机械转发或 UI 内部结构的脆弱测试。
- 每阶段完成后运行最窄相关检查，不在每个编辑后重复跑整个项目。
- 每次交付列出实际运行的命令／场景、结果、证据路径和尚未验证的内容；不复用旧架构证据宣称新功能通过。
- 实现中如果必须改变本文件已确认的范围或关键约束，先说明风险并取得用户明确同意，再更新方案。

## 11. 风险与需要验证的假设

| 风险／未知 | 原型要证明什么 | 失败时的行为 |
| --- | --- | --- |
| Windows／WSL 来源身份 | 当前 handler 能与确切窗口、pane、session 对应 | 拒绝猜测，允许明确绑定 |
| 本地通信通道 | 双向传输、访问控制、顺序、断开和恢复真实可用 | 状态标未知，不重发执行 |
| 任务归属 | 能将请求与实际消费、工具、计划和交付关联 | 普通活动只作观测，不推进需求 |
| 手动输入混入同一 run | 可识别或清楚标记共享上下文 | 不声称独占或精确作者归属 |
| 计划观测来源 | 可靠接收结构化步骤变更 | 不伪造步骤或百分比 |
| 多窗口和写入中断 | 一致写入、冲突拒绝和崩溃恢复 | 只读／待恢复，不覆盖旧资料 |
| 当前 SDK 与历史研究版本不同 | 每项集成 API 在实际版本中存在且语义匹配 | 调整实现而非修改全局模型绕过 |
| 本地审计可信边界 | 应用内历史完整但不伪称防篡改 | 明确显示校验失败或未知 |

历史研究已发现 omp extension 事件与 Tern 状态可用于集成，但还未证明本设计的端到端实时链路。`ctx.ui.openTerminal` 的已研究支持列表不包含 Tern，不能直接假设它能在此环境原位分屏；布局交给 Tern 侧处理。源码／文档中的能力必须以阶段 1 实测收敛。

## 12. 实施起点与完成定义

阶段 0–5 已实施。阶段 6 决定不迁移旧数据；只删除旧入口并保留旧 KV 与方案原样，未完成真实发布验收。下一轮若继续，应先明确是否需要迁移和选择哪个真实项目。不因当前 UI 可用就宣称交付闭环完成。

最终完成必须同时满足：

- 一个 omp＋一个工作台的默认布局；
- 可恢复、可信且不伪造的实时状态和进度；
- 每个需求的全流程设计、计划、结果和审计；
- 真实代码与验证证据，不以模型文字代替；
- 明确批准、人工验收、异常恢复与旧数据迁移；
- 全部命名验收项通过，说明和旧入口同步完成切换。
